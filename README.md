# כלי מיון, קיבוץ, שיוך ומתן-שמות למסמכים

כלי Streamlit עצמאי של ישרים סוכנות ביטוח ופיננסים.

מעלים אליו קבצים שלקוח שלח (PDF או תמונות), והוא:

1. **קורא** כל קובץ ומחלץ ממנו סוג מסמך, מוסד, בעלים, תאריכים ומספור עמודים
2. **מקבץ** קבצים שהם אותו מסמך לוגי — שלושה תלושים של אותו אדם ואותו מעסיק
   הם מסמך אחד
3. **משייך** כל מסמך לסאב-אייטם הפתוח שלו בתיק במונדיי
4. **נותן שם** לפי כללי מתן-השמות של המשרד
5. **ממזג** כל קבוצה ל-PDF אחד ומאפשר הורדה, מסודרת בתיקיות לפי יעד

ההעלאה למונדיי נשארת ידנית בשלב זה.

**הכלי נפרד לחלוטין ממנוע ניתוח דוחות האשראי.** אין לו חותמת `BUILD` משותפת
איתו, ואין לו תלות בקבצים שלו. הגרסה שלו מסומנת ב-`TOOL_BUILD` בראש `app.py`.

---

## הרצה מקומית

```bash
pip install -r requirements.txt
streamlit run app.py
```

בסרגל הצד מזינים מפתח Anthropic API, או שומרים אותו ב-secrets.

## פרסום לאינטרנט — Streamlit Community Cloud

1. העלו את קבצי התיקייה למאגר בגיטהאב
2. היכנסו ל-https://share.streamlit.io, חברו את המאגר ובחרו את `app.py`
3. תחת **Settings → Secrets** הוסיפו:
   ```
   ANTHROPIC_API_KEY = "sk-ant-..."
   ```
4. תקבלו כתובת קבועה שאפשר לשלוח לעובדת

## איך עובדים עם הכלי

### הקשר התיק — התיבה החשובה ביותר

בסרגל הצד יש תיבה בשם **"סאב-אייטמים פתוחים"**. מדביקים בה, שורה לשורה, את שמות
הסאב-אייטמים שהתיק מחכה להם — בדיוק כמו שהם מופיעים במונדיי.

```
תלושי שכר 3 חודשים אחרונים — זאודה אנדרגה
תלושי שכר 3 חודשים אחרונים — זאודה טלי
עובר ושב 3 חודשים — בנק מזרחי טפחות בע"מ (משותף)
אישור ניהול חשבון — בנק מזרחי טפחות בע"מ (משותף)
```

**בלי הרשימה הכלי רק מסווג ולא משייך.** עם הרשימה הוא גם מחליט לאן כל מסמך
שייך, וגם מדייק את הזיהוי.

הרשימה משמשת בשני מקומות שונים, וההפרדה ביניהם מכוונת:

- **בקריאת הקובץ** מועברים ממנה **רק שמות בעלי התיק**, לצורך זיהוי בעל המסמך.
  רשימת המסמכים עצמה לא מועברת — כשהיא הועברה, המודל נמשך להתאים את המסמך
  לאחד הפריטים ברשימה במקום לקרוא מה הוא באמת, ותלוש שכר זוהה כדוח משכנתא.
- **בשלב הקיבוץ** מועברת הרשימה המלאה, ושם מתבצע השיוך.

### שלושה סוגי פלט

| המקטע | מה נמצא בו |
|---|---|
| **שויך ומוכן להעלאה** | זוהה בוודאות ושויך לסאב-אייטם |
| **מסמכים נוספים** | זוהה בוודאות, אך אין לו יעד ברור ברשימה |
| **לבדיקה ידנית** | הזיהוי עצמו לא ודאי |

ובתחתית: **"עדיין חסר מהלקוח"** — סאב-אייטמים שלא קיבלו שום מסמך. זו בדיוק
הרשימה שנשלחת בתזכורת.

### שני הסליידרים

- **סף ביטחון** — מתחתיו המסמך מסומן "לבדיקה ידנית"
- **סף שיוך** — מתחתיו המסמך הולך ל"מסמכים נוספים" במקום להיות משויך

**"לא יודע" עדיפה על ניחוש.** מסמך שהועלה לסאב-אייטם הלא נכון גרוע בהרבה
ממסמך שממתין לטיפול ידני.

## החלטות תכנון שכדאי להכיר לפני שמשנים

### קריאה ויזואלית של PDF

כל PDF מומר לתמונות ונשלח כתמונה, לא כמסמך. שתי סיבות:

**איכות.** מסמכים ישראליים רבים — תלושי שכר במיוחד — נושאים שכבת טקסט בקידוד
עברי ישן שנקראת כג'יבריש לטיני. בנוסף, שם הבנק בדוחות תנועות יושב בלוגו שהוא
תמונה ולא מופיע בטקסט כלל, והמודל היה מנחש אותו לפי שכיחות מילים בשורות
התנועות.

**עלות.** שליחת PDF כמסמך גורמת לשרת לחייב **גם על הטקסט וגם על תמונה של כל
עמוד**. תמונות בלבד עולות פחות מחצי.

הכלי מאבחן לבד את שכבת הטקסט ובוחר דיוק בהתאם: טקסט שבור או מסמך סרוק נקראים
בדיוק גבוה, טקסט תקין בדיוק נמוך יותר בתוספת הטקסט המחולץ. **אין מה להגדיר.**

### פורמט התשובה — שורות, לא JSON

המודל מחזיר `מפתח: ערך`, שורה לשורה. **לא JSON.**

הסיבה: שמות ישראליים מכילים גרש כפול — בע"מ, עו"ש, נספח "יב" — והוא תו מבנה
ב-JSON. כל טלאי שתיקן מקרה אחד נשבר על מקרה אחר. בפורמט שורות הגרש הוא תו רגיל
ואין לו מה לשבור. מה שמפריד בין שדות הוא סוף שורה, ובין מפתח לערך הנקודתיים
הראשונות — שניהם לא מופיעים בתוך שמות מסמכים.

הפרסר סלחן: שורה שאינה מזוהה מדולגת, ולכן פתיח או הסבר מהמודל אינם מפילים את
הקריאה. אם בכל זאת יחזור JSON — יש נפילה חזרה שתקרא אותו.

### שני חוקי ברזל בקיבוץ

1. **לעולם לא לאחד מסמכים של שני אנשים שונים**
2. **לעולם לא לאחד מסמכים משני מנפיקים שונים** — שני מעסיקים, שני בנקים

אדם אחד יכול לעבוד בשני מקומות, ואלה שני מסמכים נפרדים. **שניהם יכולים
להיות משויכים לאותו סאב-אייטם, וזה תקין.**

### temperature אינו בשימוש

הפרמטר שהיה מבטיח תשובה זהה לאותו קלט **בוטל במודל הזה** — השרת מחזיר עליו
`deprecated for this model`. אין דרך לעקוף. מה שכן נשאר הוא כיבוי החשיבה
הפנימית, שחוסך טוקני פלט ומונע מצב שהחשיבה בולעת את כל תקרת האורך והתשובה
חוזרת ריקה.

בפועל, השימוש בדגם המדויק לכל הקבצים נתן את עיקר היציבות.

## מד עלות

מופיע אחרי כל הרצה, מתחת להודעת הסיום: כמה קריאות, כמה טוקני קלט ופלט, וכמה
זה עלה בדולרים. **המספרים מדווחים על ידי השרת ולא מאומדן.** קבצים שנשלפו
מהזיכרון אינם נספרים.

המחירון ניתן לעריכה בסרגל הצד.

**סדרי גודל למדידה בפועל:** תיק של בני זוג עם אחד עשר קבצים עלה כ-0.19 דולר.
בנפח של כשלושים תיקים בחודש, זה בסביבות עשרה עד חמישה עשר דולר לחודש.

## אבחון תקלות

בכלי שלוש תיבות אבחון. **הן קיימות כי בלעדיהן מנחשים.**

| התיבה | מתי מופיעה | מה יש בה |
|---|---|---|
| קבצים שהקריאה שלהם נכשלה | קובץ יצא "אחר" עם ביטחון אפס | תשובת המודל הגולמית לאותו קובץ |
| מה המודל באמת החזיר | שלב הקיבוץ נכשל | תשובת הקיבוץ הגולמית, כולל הניסיון החוזר |
| פרמטרים שנדחו | הספרייה או השרת דחו פרמטר | נוסח השגיאה המדויק |

**אם משהו יוצא עקום — פתחו את התיבה הרלוונטית לפני שמנחשים.** תשובה ריקה
מהמודל מוצגת כדיווח אבחוני ולא כמחרוזת ריקה, כולל סיבת העצירה ומספר טוקני
הפלט.

## מגבלות ידועות

- תומך ב-PDF, JPG, PNG, WEBP, GIF. קובצי HEIC מאייפון דורשים המרה מראש
- כל קובץ נשלח בנפרד, אז חבילה גדולה תיקח כמה עשרות שניות
- **אין עדיין בדיקת שלמות.** הכלי יודע אם הגיע משהו לסאב-אייטם, אבל לא כמה.
  לקוח ששלח שני תלושים מתוך שלושה ייחשב כמכוסה. השדות הנדרשים לבדיקה
  (`balance_start`, `balance_end`, מספור עמודים, ספירת עמודים אמיתית) כבר
  נאספים — הלוגיקה עצמה עוד לא נבנתה
- הכלי אינו מדבר עם מונדיי. אין לו נקודת כניסה, ולכן Make אינו יכול לפנות אליו

## מה בתור

1. **בדיקת שלמות** — רצף תאריכים, טווח מבוקש, ועדכניות מול מועד השליחה
2. **שכבת שרת** — נקודת כניסה שתאפשר ל-Make לשלוח קבצים ולקבל תוצאה
3. **חיבור לאוטומציה** — קליטת מסמכים מוואטסאפ והעלאה אוטומטית לסאב-אייטמים
